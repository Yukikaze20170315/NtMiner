# 2.8.9.5 构建中未开始挖矿时的 LogPrint 空队列忙循环

## 问题与提交范围

本地一个程序集版本为 **2.8.9.5** 的开源矿工构建，在尚未开始挖矿、没有 SRBMiner 进程运行时，主程序持续消耗 CPU。按进程、线程累计 CPU 时间及 ETW 调用栈定位，主要来源是 `NTMiner.Views.MainWindow.LogPrint()`。

**本报告不声称当前公开 `master` 包含该缺陷。** 本次核对的 GitHub 提交 `714fd0f5b7114ddad4b03ca0ccb76ccc0ae74a8d` 的版本常量为 2.8.7，其中 `MainWindow.xaml.cs` 没有 `LogPrint`，源码树也未见 `NTMinerFile` 项目。Coding 镜像提交 `a0d9e844861f8771bf9f2ae28741d1b084082590` 也未找到对应实现。尚未建立所测二进制与公开仓库提交或官方发布产物之间的可验证对应关系，因此请维护者先确认该构建及其源码来源。

本提交提供缺陷证据、最小修复示例和本地验证结果，供维护者定位对应版本后移植。它只新增诊断文档，**不会因合并本文档而修改 `master` 的程序行为**。

## 复现条件和采集方法

- Windows 11 build 26200，16 核 / 32 线程 CPU。
- 启动主程序，保持未挖矿状态，不启动矿工内核。
- 连续约 62 秒读取进程和线程的累计用户态/内核态 CPU 时间，以增量判断占用。
- 对原始进程使用 WPR CPU profile，分析约 55 秒的采样栈和上下文切换，并通过 CLR rundown 解析托管方法名。
- 原始主程序 SHA256：`C5F243A1D7A337630A078876852BD804F7E54F16F1E34072AD164116BFD89729`。
- 所测内嵌 `AppViews0.dll` 的程序集版本为 `1.0.0.38635`，`LogPrint` 方法 token 为 `0x06000045`。

初次 61.9025 秒基线中，主程序 CPU 时间增加 60.859375 秒，其中单个日志工作线程增加 60.578125 秒；该线程 63 次状态快照均为 Running。

54.9 秒 ETW 分析窗口内，该线程的 54,856 个 CPU 样本中，98.4468% 位于以下三个方法：

| 叶子热点 | 样本数 |
| --- | ---: |
| `ConcurrentQueue<T>.get_IsEmpty()` | 25,089 |
| `NTMiner.Views.MainWindow.LogPrint()` | 16,111 |
| `NTMinerFile.MainFile.GetInstance()` | 12,804 |

该线程实际为 CLR 线程池工作线程；不能仅凭 `MainWindow` 方法名把它当作 UI 消息线程。此窗口没有发现 SRBMiner 或 taskkill 实例，因此这里分析的是未挖矿基线。

## 直接原因

在得到本机用户授权后，针对原始二进制进行有限的方法级分析，发现 `LogPrint` 有以下分支：

```text
IL_000c: call MainFile.GetInstance()
IL_0011: ldfld MainFile.LogQue
IL_0018: callvirt ConcurrentQueue<Tuple<string, ConsoleColor>>.TryDequeue(...)
IL_001d: brfalse.s IL_000c
```

当队列为空、`TryDequeue` 返回 false 时，执行流立即跳回取队列的位置，没有等待或退避。该路径形成空队列忙循环。`MainFile.GetInstance()` 在此只是单例访问；方法名不代表实际文件 I/O。采样中的 `IsEmpty` 来自队列内部调用。

## 最小修复示例

只在没有取到日志时等待，再继续循环；成功取日志后的过滤、颜色、长行拆分和 UI 输出流程保持不变。下面是对应源码结构的示例，**不是声称来自当前 `master` 的逐行补丁**：

```csharp
while (true) {
    Tuple<string, ConsoleColor> item;
    if (!MainFile.GetInstance().LogQue.TryDequeue(out item)) {
        Thread.Sleep(20);
        continue;
    }

    // 保留此版本现有的日志处理流程。
}
```

本地实验只把失败分支改为经过 `Sleep(20)` 再返回原循环，成功分支保持原样。等待 20 毫秒是较小的修复范围，并不是日志显示延迟的严格上限；操作系统调度及 UI 工作仍可能增加延迟。若维护者掌握生产者与退出生命周期，后续可考虑事件驱动的阻塞消费，但需要同时处理信号和退出路径，不属于此次验证过的最小改动。

## 验证结果

### 实际方法 IL 的隔离测试

将原版及修复后的实际 `LogPrint` IL 分别移入独立测试容器，仅将单例和 UI 输出依赖映射为内存队列及输出收集器，不启动完整矿工、GPU 或网络逻辑。

| 约 5 秒空队列观察 | 原版 | 修复版 |
| --- | ---: | ---: |
| 墙钟时间 | 5009.008 ms | 5008.043 ms |
| 进程 CPU 时间增量 | 4968.750 ms | 0.000 ms |

0.000 ms 表示低于本次系统 CPU 计账粒度，不是数学上的绝对零。

两版均通过普通日志、150 字符长日志的 70/70/10 拆分、颜色过滤、100 条突发日志顺序、队列变空后由另一线程追加日志的检查；输出 106 段，队列最终为空。修复版首次日志到达的观测值约 46.6 ms，未承诺严格 20 ms 的端到端上限。

### 本机完整程序的未挖矿验证

在用户授权并备份原程序后，只替换日志空队列失败分支，重启主程序，保持未挖矿状态：

| 指标 | 修复前复测 | 修复后 |
| --- | ---: | ---: |
| 观察墙钟时间 | 60.9162293 s | 61.9414842 s |
| 主程序 CPU 时间增量 | 60.171875 s | 0.343750 s |
| 日志线程 CPU 时间增量 | 60.062500 s | 0.046875 s |
| 日志线程状态快照 | 62 次 Running | 63 次 Wait / ExecutionDelay |

按墙钟时长归一化，主程序自身 CPU 消耗下降约 99.44%，日志线程下降约 99.92%；这不是全机 CPU 使用率下降百分比。

修复后的 CLR rundown 和 ETW 把等待线程对应回 `LogPrint`；上下文切换栈进入 `ThreadNative::Sleep` → `SleepEx` → `NtDelayExecution`。两次 ETW 的丢失事件均为 0。补丁结构校验显示目标模块仅一个方法体改变，外层主程序方法体未改变，只有该模块的压缩资源发生变化，其他嵌入资源哈希一致。
